## Go build caches inside the cache volumes (2026-11-02): step 3d of the 4-hourly GC, in git only, NOT installed

**Why.** `fleet-job-cache-gucapi-gocache` is the Go build cache of the go-url-categorizer-api CI and test jobs. It went from 17 GiB (10-29) to 80 GiB (10-31), was trimmed by hand to 44 GiB, and was 70.8 GiB at 2026-11-02 05:22Z and 80.4 GiB at 08:47Z: 1.8 to 2.5 GiB an hour on a quiet evening, 2.8 on a CI burst (five containers used it at 05:22Z, none at 08:47Z). The root rose 36 GiB in 10.7 hours (401 to 437 of 591 GiB used); the CI load controller stops scheduling at 10 % free. The volume is in use most weekday hours, so step 3c (whole volumes that nothing wrote to for 3 days) never touches it and nothing bounded its size. A one-off `fleet-job cache prune --yes` at 08:53Z (defaults, found idle) took it from 80.4 to 23.8 GiB and the root from 78 to 66 % used; it refills at the rates above.

**What step 3d is.** `docker-build-gc.sh` calls `fleet-job-caches-trim.sh` right after 3c (only if it is installed and executable, with its own `timeout 1800`). That script runs `fleet-job-caches.sh`, go-fleet-job's own program (`fleet-job cache prune` is the same file), with fixed arguments and prints one line per volume that changed and one line of totals. The program only touches volumes called `fleet-job-cache-*`, and inside them only a Go build cache (a directory whose `README` is the go tool's): files, oldest first, until it is under the cap; never a directory, `README` or `trim.txt`; never a file used within an hour, and while a container uses the volume never a file used within the floor. It walks each volume in a throw-away root container (`--pull never --network none --cpus 1 --memory 512m`; those containers are children of dockerd, so the unit's Nice and idle I/O do not reach them) and mounts a volume only if `docker volume inspect` still finds it.

| Setting (environment of `fleet-job-caches-trim.sh`) | Default | Why |
|---|---|---|
| `CACHE_TRIM_MAX_GIB` | 20 | 14 full runs of the go-url-categorizer-api test suite (one run writes 1.4 GiB). A trimmed entry is a cache miss: the next job rebuilds it, about 3 minutes once (360 s cold, 180 s warm, measured by go-fleet-job) |
| `CACHE_TRIM_BUSY_HOURS` | 12 | nothing used within 12 h goes while a container uses the volume (the program's minimum is 6; go-fleet-job's reasoning: the go tool refreshes an entry's time before it hands out its path, so a running action holds an entry at most an hour old plus its own run) |
| `CACHE_TRIM_UNUSED_DAYS` | 30 | the program removes a volume that no container refers to and nothing wrote to for this long, and it has no switch against that. Whole-volume removal is meant to stay with step 3c (3 idle days), so this is ten times that: a backstop that can only act if 3c did not. The step refuses less than 4 |
| `CACHE_TRIM_IMAGE` | `golang:1.27 golang:1.26` | a list (one to six): the first image that is on the host is the one the walking containers run in (it needs GNU `find`; the program itself never pulls); when none is on the host the first is pulled, see "The image" below |
| `CACHE_TRIM_PULL` | 1 | 0 turns the pull off (a missing image is then a `WARNING` skip, exit 3); a dry run never pulls whatever this says |
| `CACHE_TRIM_MIN_FREE_GIB` | 5 | a pull is made only with this many GiB free where docker keeps its images, because the GC exists for a disk that fills (0 = no check) |
| `CACHE_TRIM_PROM_DIR` | `/var/lib/prometheus/node-exporter` | where a full live run writes `fleet_job_caches_trim.prom`; a directory that is not there is no error; a dry run or `CACHE_TRIM_VOLUME` writes nothing |
| `DRY_RUN` (0 or 1, anything else is refused), `CACHE_TRIM_VOLUME` (the part after `fleet-job-cache-`) | 0, all | `DRY_RUN=1` runs the program's `plan`: it lists what it would do, mounts every volume read-only, never pulls an image and writes no metric. **Only this helper has a dry run: `docker-build-gc.sh` has none, so never set `DRY_RUN=1` on the whole GC (the other steps would still run for real).** |

**The image (2026-11-03, read-only evidence).** The program runs its walking containers with `--pull never`, so a golang image has to be on the host, and an image that no container uses is removed by every `docker image prune -a` whose age it exceeds. Two scheduled pruners do that with the same rule, `until=168h`, which counts from the image's *creation* date and not from its last use: step 3 of this GC (every 4 hours) and `fleet-docker-prune` (daily, 04:30 plus up to 30 minutes; it ran at 04:42Z on 11-03). On 2026-11-03 07:19Z the host had `golang:1.27` and `golang:1.27.3` (one image, `a301d0a60356`, four containers running on it) and `golang:1.26` (`593dc3550e05`, one container), all created 2026-10-28 03:15Z: all three become prunable on **11-04 03:15Z**, and the GC runs at 04:23Z, when CI is quiet (the 04:23Z run on 11-03 found no container, even a stopped one, on any cache-named volume). A prune with a shorter age takes an unused image sooner: a session pruned VM 130 with `docker image prune -a -f --filter until=24h` at 22:46Z on 11-02 (agent history; the daemon log has four golang digests at 22:47Z), and `golang:1.26`, the first wrapper's default image, was missing at 23:10Z. It is there again on 11-03 (one container runs on it). With the first wrapper a missing image meant `SKIPPED` and exit 0, so after step 4 step 3d could silently never run. The wrapper now (1) uses the first of `golang:1.27 golang:1.26` that is on the host (the images CI runs; `golang:1.27.3` is a second tag of the same image, so it can never be there when `golang:1.27` is not), (2) pulls the first one when none is, and (3) says `WARNING` and exits 3 when it still cannot. **Why a pull and not only a loud failure:** the list cannot help when all of them go together (they share a creation date), and a loud failure leaves the hot volume untrimmed until some job happens to pull an image, which on an idle night or weekend is hours (the hot volume grows 1.8 to 2.8 GiB an hour). The pull is cheap here: the daemon asks the LAN registry mirror `10.10.10.80:5001` first and then mirror.gcr.io (`docker info`; the mirror answered in 8 ms on 11-03 and has `library/golang`), so it is not a Docker Hub download and not subject to its rate limit. It is bounded (300 s), made only with room on the disk, never in a dry run, and switched off by `CACHE_TRIM_PULL=0`. Its cost is a pull of about 0.9 GB from the mirror whenever the image has been pruned since the last run: at most once per GC run, in idle hours, and only while upstream's image is more than 7 days old (a fresh upstream build lives a week). Neither prune is changed, so no other image is protected or exposed by this. A container that refers to the helper image (a stopped one is enough: docker's documentation says an image that a container, stopped or not, refers to is not unused) would stop that cycle, but it is not added here because it cannot be tried read-only; if the journal shows a pull on every run, that is the next step. **Visible when it cannot run:** every such line starts with `WARNING` (`grep WARNING` in `journalctl -u docker-build-gc.service`), the exit status is 3 (1 for a failed volume or an incomplete report), and a full live run writes `fleet_job_caches_trim.prom` into node_exporter's textfile directory (`last_run_timestamp_seconds`, `last_result` 0 ran / 1 failed / 2 skipped, `freed_bytes`, `volumes_over_cap`), as `fleet_docker_prune.prom`, `wt_gc.prom` and `docker_network_gc.prom` do on this host. The GC ignores the exit status on purpose: a skip heals itself with the next pull, and a failing unit would page for it. **The alerts on the metric are a separate change, not part of the one that added it:** see "Alerts on the trim" at the end of this section.

**Design choice: vendor go-fleet-job's program and call it from the GC, not extend `idle-cache-volumes-trim.sh`.** That script cannot see inside a volume: it removes a whole volume that no container has attached (stopped ones count) and whose top two directory levels were not written for 3 days. Taking files out of a Go build cache by age and size, never what a running build may hold, is a different job, and the program already does it with tests (go-fleet-job reports 355 top-level tests and 210 mutations that each turn a test red; I have not re-run them). Extending the script would be a second implementation of the README signature check, the age profile and cut, the re-judging of each file as it is removed, the floor for volumes in use, docker's own refusal and the inspect-before-mount guard, beside a different idle rule; a fix in either would not reach the other. Vendoring keeps one implementation: the program stays byte-identical to its tag (pinned below), and the only code of this repository is the thin wrapper (settings, refusals, a summary), which has its own tests. Whole-volume removal stays with 3c because 3d runs after it in the same pass and its own limit is 30 days.

**What to expect (arithmetic from the measured rates, not a measurement).** With the floor at 12 h the cap is not always met: 12 h at 1.8 to 2.8 GiB an hour is 22 to 34 GiB of entries used within the floor, and a 4-hourly run lets the volume grow by 7 to 11 GiB more before the next one, so the hot volume should peak around 35 to 45 GiB (a line says `cap_unmet=yes` when the floor held the cap back) instead of 80 GiB and rising. A tighter bound is `CACHE_TRIM_BUSY_HOURS=6` (the program's minimum), a shorter timer for this step, or both; that is a decision, not made here.

**The vendored program, and how to update it.** Vendored from baditaflorin/go-fleet-job tag v0.5.0, commit c29b3ccf063902ec67dd795b3a97409f9d7353be, file pkg/remote/caches.sh, sha256 aa3927be96de8fc46b64b5b854713d18bff976d66803c13721c9936c4e7c5265 (`fleet-job-caches.sh` is that file, byte for byte; the same hash is its entry in `files.sha256`). To update: read the new tag's `pkg/remote/caches.sh` (its usage block is the interface this step relies on: `MODE MAX_AGE MAX_BYTES MIN_KEEP IMAGE [NAME [BUSY_KEEP]]`) and `docs/VERIFICATION.md`, then `git -C <go-fleet-job checkout> show vX.Y.Z:pkg/remote/caches.sh > files/usr/local/bin/fleet-job-caches.sh`, put the new tag, commit and sha256 in the sentence above and the hash in `files.sha256`, and run `tests/test_docker_build_gc_cache_trim.py`: it fails until the file, this sentence and the manifest agree, and it audits again that the program removes only cache files (`find -delete`) and one named volume (`docker volume rm "$v"`). A fix to the program belongs in go-fleet-job, never in this copy.

**What is verified, and what is not.** `tests/test_docker_build_gc_cache_trim.py` runs the wrapper against a fake docker (images, `docker pull`, `docker info`) and, where GNU find exists (the 0mcp build host), the real vendored program against sparse-file caches in a temp directory: the order of the image list, a pull when none is on the host (once, never in a dry run, never with `CACHE_TRIM_PULL=0`, never without room or after a failed pull), the `WARNING` lines and exit 3, the textfile metric (written by a full live run only, 0644, no temporary file left); a cache over the cap loses its oldest files down to the cap; while a container uses the volume nothing used within 12 h goes and the cap can stay unmet; a dry run changes nothing and mounts read-only; volumes without the prefix, caches that are not Go's and young files are untouched; a volume is removed only after 30 idle days (a pinned backstop); a volume docker lost is never mounted. go-fleet-job's own evidence for the program: a real read-only plan on this host on 2026-11-01 08:57Z while two containers used the hot volume (without the floor `skip`, with `--busy-age 12h` `trim` 26.3 GiB), and `scripts/go-cache-trim-race-check.sh` (200 rounds in a throw-away `golang:1.26` container, 705 cache entries, every round makes all entries look 8 hours old and runs `go build -x` and `go vet -x` while twice the floor-6h trim runs): 0 rounds in which the build failed; the trim took 96,405 of 140,826 entries and the builds redid 16,507 compiles and vets (entries taken before they were read are misses). **What was run for real:** at 08:53Z on 2026-11-02 a `cache prune --yes` with the defaults on volumes that were idle (80.4 to 23.8 GiB in 27 s), and at 23:23Z the step-3 run above, the first real `--busy-age` trim (reported by the session that ran it: 33,183 MiB in 48 s, 64.1 to 30.3 GiB, `cap_unmet=yes`, exit 0; the effect on CI was not examined here). The hot volume grew from 23.8 GiB to 64.1 GiB in those 14.5 hours, 2.8 GiB an hour, the burst rate used above, and the trim left 30.3 GiB, inside the 22 to 34 GiB that the arithmetic gave for what a 12 h floor keeps. **What is not verified:** the pull path (no image was removed from the host to try it: the tests use a fake docker, and the registry mirror was only read, not pulled from); the metric on the live node_exporter (the tests write it to a temp directory, the format follows `fleet_docker_prune.prom`); how often the image is really missing at GC time (the metric will say). The race check is evidence, not proof: it used a cache of 705 entries and not the real one (175,000 to 280,000 files), builds of a few seconds, one container; the go tool's own trim has the same window (an entry removed between the go tool getting its path and opening it). Nothing measured the effect of a 20 GiB cap with a 12 h floor on the hit rate of real jobs over days. The tests were run by hand, on the 0mcp build host and on a Mac (GNU-find tests skipped there), with a sweep of one-line breakages of the wrapper, the GC script and the vendored file: the pre-push gate's checks do not run `tests/`, and no pipeline does.

### Alerts on the trim

`config/prometheus/rules/fleet-job-caches-trim.yml` (unit tests `tests/promtool/fleet_job_caches_trim_rules_test.yml`; where it is applied and how to roll it back: `docs/runbooks/fleet-observability.md#build-host-cache-trim-alerts`) reads the four gauges of `fleet_job_caches_trim.prom` on the 0mcp Prometheus, which scrapes the VM as `host="docker-build-lv3"` (the 0docker one sees the same file as `host="0mcp-builder"` and gets no rule). Until it, nothing read the file: a failed or skipped run, a stopped timer, a missing file or a volume stuck over its cap told nobody (on 2026-11-02 the step would have been skipped silently). **The rule file is in git only: it is not on the monitoring VM, so nothing below fires yet.** Step 3d itself is live: it has been in the GC since 2026-11-03 10:05Z and has run on its own three times (12:25, 16:27 and 20:27Z: result 0, nothing over the cap, 29,286, 2,722 and 3,303 MiB freed), so the staged plan above has been applied through step 4.

| Alert | Fires when | Severity |
|---|---|---|
| `FleetJobCachesTrimFailed` | the last full run wrote result 1 (a volume failed, docker did not answer or the report was incomplete) or 2 (skipped: the program, docker or a golang image is missing and could not be pulled) and it stayed for an hour. Only a full run rewrites the file, so a bad value stays up to 4 hours | warning |
| `FleetJobCachesTrimStale` | no run has written the file for 9 hours (two missed runs of the 4-hourly timer plus slack), for 30 minutes. A run that the step's 30 minute timeout kills writes nothing, so it ends here and not in `FleetJobCachesTrimFailed` | warning |
| `FleetJobCachesTrimMissing` | no `fleet_job_caches_trim_last_run_timestamp_seconds` series for `docker-build-lv3` for a day (the stale rule cannot fire on a series that does not exist) | warning |
| `FleetJobCachesOverCap` | `fleet_job_caches_trim_volumes_over_cap` above 0 at every run for 24 hours (six runs in a row). In a CI burst it is above 0 for hours by design (the 12 hour floor beats the cap), so a short delay would be noise | info: Alertmanager drops it and it shows in the Prometheus alert list; make it a warning once real bursts have been seen |

What to do. Read the last runs first: `ssh 0mcp_docker_build 'sudo -n journalctl -u docker-build-gc.service --since -5h --no-pager | grep fleet-job-caches-trim'` (`sudo -n` is needed: `ops` is not in the `systemd-journal` group, and without it `journalctl` answers "No entries" and exits normally, which reads as a quiet run; the GC keeps only the last 12 lines of the step) and `ssh 0mcp_docker_build 'cat /var/lib/prometheus/node-exporter/fleet_job_caches_trim.prom'` (the four numbers, rewritten by every full run).

- `FleetJobCachesTrimFailed`: the `WARNING` lines name the volume or the image. A `WARNING: SKIPPED` (result 2) means the program, docker or a golang image is missing and the bounded pull did not work (it needs 5 GiB free; `ssh 0mcp_docker_build 'docker image ls golang'`). The listing the next run would act on is the dry run of step 2 above (it holds the GC's lock, so do it more than 10 minutes before the timer fires). A one-off cause clears with the next timer run, at most 4 hours later, and the alert resolves with it.
- `FleetJobCachesTrimStale`: `ssh 0mcp_docker_build 'systemctl status docker-build-gc.timer docker-build-gc.service --no-pager; ls -l /usr/local/bin/fleet-job-caches-trim.sh'`. A script without the `x` bit means step 3d was switched off (see the last bullet: the alert is then right). Otherwise read the whole journal of `docker-build-gc.service` for a GC that died before step 3d or a step that hit its timeout; the service runs under `flock -n /run/lock/docker-build-gc.lock`, so a hand-run dry run that held the lock made one timer run fail, which alone is not enough for this alert (two in a row are).
- `FleetJobCachesTrimMissing`: `ssh 0mcp_docker_build 'ls -l /var/lib/prometheus/node-exporter/'` (the wrapper writes the file for a full run only and treats a missing directory as no error), then in Prometheus `up{host="docker-build-lv3"}` (the VM is not scraped), `node_textfile_scrape_error{host="docker-build-lv3"}` (node_exporter dropped a malformed file; 0 on 2026-11-03) and `node_textfile_mtime_seconds{host="docker-build-lv3"}` (the file's own time).
- `FleetJobCachesOverCap`: the journal lines with `cap_unmet=yes` name the volume (`ssh 0mcp_docker_build 'sudo -n journalctl -u docker-build-gc.service --since -5h --no-pager | grep cap_unmet'`, or `fleet-job cache ls --host 0mcp_docker_build`). A few runs in a burst are expected (the hot volume peaks at 35 to 45 GiB); a day of it means the cap and the floor no longer fit the load (raise `CACHE_TRIM_MAX_GIB`, lower `CACHE_TRIM_BUSY_HOURS` to 6, the program's minimum, or shorten the timer for this step: all decisions, none made here) or a container holds a volume busy for good (`docker ps -a --filter volume=fleet-job-cache-NAME`). The root-filesystem alerts (`FleetRootFilesystemLow`, `FleetRootFilesystemCritical`) are what notifies when the disk is really at risk.
- To switch the trim off on purpose (the undo of step 4): `ssh 0mcp_docker_build 'sudo chmod -x /usr/local/bin/fleet-job-caches-trim.sh'`. The file keeps what the last run wrote, so `FleetJobCachesTrimStale` fires 9 hours 30 minutes after the last run that wrote it: silence it in Alertmanager for as long as the trim is off rather than deleting the rule, and remove the silence when the `x` bit is back.

Where the delays come from and what is not known is in the header of the rule file: the series were less than a day old when it was written (three runs, all result 0, none over the cap) and no alert has ever fired on them, so the delays are reasoning checked against that, not a back-test.

## Not in git, on purpose (secrets and state): what to do when the VM is rebuilt
* Woodpecker agent token `/opt/woodpecker-agent-tokens/agent-90.token` and the agent's own config volume (`woodpecker-0exec-agent_woodpecker-agent-config`): reissue the agent in the Woodpecker server (`fleet-runner woodpecker` verbs on the builder), the agent registers itself again.
* Gitea runner registration token: **kept nowhere**. The runner `docker-build` is registered through `/opt/gitea-runner/data/.runner` (keep that file: it is its identity); `act_runner` reads the token only when that file is missing. The compose file
  used to hold a global (instance-wide) registration token as a literal; it was found on 2026-10-22, invalidated on 2026-10-23 (Gitea 1.25.5 on `runtime-control-lv3`, VM 192: the row was deleted from `action_runner_token`) and removed from the live file and
  its three August backups. To register a runner again, generate a token on the Gitea host (`docker exec -u git gitea gitea actions generate-runner-token`), pass it once to `act_runner register`, and do not store it.
* OpenBao agent inputs and rendered credentials: `/opt/gitea-runner/openbao/*`, `/opt/gitea-runner/credentials/renovate`, `/opt/woodpecker/openbao`, `/run/0mpc-secrets/woodpecker`: reissue the agents' AppRole credentials in OpenBao.
* Nomad agent TLS material `/etc/mcp/nomad/tls/*` (agent key and certificate): only if Nomad is ever really used again; today it is not.
* Caches, images and BuildKit state (Go caches, `/opt/builds`, buildx builder volumes, test containers, the scratch git clones in `/home/ops`): rebuilt by the builds themselves. The first builds after a rebuild are slower.
