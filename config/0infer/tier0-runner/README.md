# Tier-0 runner on infer-tier0 (VM704)

The actor that runs the 0docker failover chain **without a person, without the operator's Mac and without the offline key**, and proves it every day.
Why here: VM704 is independent of 0docker, of 0mcp and of the builder (CT108 stops ~8-10 min every night for its backup). The Mac sleeps (a scheduled task did not fire).

## What runs
| Piece | What it does | Schedule |
|---|---|---|
| `bin/tier0-run SCRIPT [args]` | runs a script from the fleet-state clone as `t0runner` with the sealed key, logs to `/var/log/tier0-runner/` | on demand |
| `bin/tier0-runner-sync` | fast-forwards `/opt/tier0-runner/fleet-state` (sparse clone, read-only deploy key) to master; a commit whose scripts do not `bash -n`/compile is rolled back | every 15 min |
| `bin/tier0-rehearsal-daily` | `tier0-failover.sh --rehearse` (vault+keystore, slice, standby gateway), teardown after any failure, then the DNS plan check; exports metrics | daily 05:20 UTC |
| `bin/tier0-edge-compat` | `tier0-edge-compat.sh`: builds the standby gateway and vault configs from the newest production gateway snapshot with the REAL builders and runs the edge's own `nginx -t` on them in a private mount namespace with overlay mounts (nothing is written to the edge, nothing reloaded); exports `tier0_runner_edge_compat_*`. Skipped while the chain lock is held. Exit 5 = the edge REJECTS the config (critical alert), 6 = could not run (warning) | hourly at :50 |
| `bin/tier0-vault-handback-rehearsal` | `tier0-vault-handback.sh --rehearse`: a scripted outage from real rows of the newest vault snapshot, merged with `vault-merge.py`, then the REAL vault image (throwaway container on the 0mcp standby host) must verify every row of the merged database; exports `tier0_runner_vault_handback_rehearsal_*`. Waits up to 15 min for the chain lock. Exit 5 = failed, 3 = could not run | daily 05:58 UTC |
| `bin/tier0-dns` | DNS stage: `status`, `plan`, `failover --to IP [--only FQDN,..] --apply`, `failback [--file F] --apply` (exact inverse from the revert file), `failback-git` (guarded fallback). Token from the LOCAL vault standby via stdin only | on demand |
| `bin/tier0-dns-drill` | wet drill on one throwaway name (`t0-drill.example.net`): create, selective failover, verify at the authoritative server, exact failback, idempotent, delete | monthly, 1st 05:41 UTC |
| `bin/tier0-secret` + `tier0_secret.py` | prints one secret from the local vault standby (starts/stops it under the drill's lock) | called by tier0-dns |
| `controller/tier0_controller.py` | SHADOW controller: decides "is 0docker down?" from two vantage points, records `WOULD RUN ...`, executes nothing. Rule in the file header; 8 tests | every minute |
| `executor/tier0_executor.py` | the part that ACTS on the controller's decision: precheck, vault, slice, gateway, DNS, verify, with a fence before every effectful step; modes `shadow` (default) / `sim` / `live` in `/etc/tier0-executor/mode`; `status`, `plan`, `ack` | every minute (shadow) |
| `scripts/tier0/tier0-failback.sh` (fleet-state; run by an operator or agent with ssh to the runner, the standby host and the returned primary, NOT by a timer) | the FAILBACK after a failover: `--check` (read-only readiness: executor FAILED_OVER, primary NORMAL 30 min, DNS revert, vault handback plan) and `--execute --yes-failback` (vault handback pass 1, `tier0-dns failback`, drain, pass 2, standby teardown, `tier0-executor ack`, re-arm; resumable; each failure stops at a safe point). Never run on a real failover yet | on demand |
| `executor/tier0_sim.py` | full-cycle SIMULATION on throwaway objects (real stages in rehearse flavour, real DNS API on `t0-sim.example.net`): `clean` (outage, failover, recovery, exact failback, cleanup) and `abort` (primary answers again after the vault stage) | clean daily 05:35 UTC, abort Sundays 05:50 |

## Who decides, and the rule
Frozen rule (same inputs, same decision): a vantage point is UP if any probe succeeded, DOWN if all failed, UNKNOWN if it could not be used (UNKNOWN never counts as DOWN). A tick is DOWN only if ALL vantage points are DOWN. Five consecutive DOWN ticks = one failover decision (alert `Tier0FailoverDecisionPrimaryDown`); thirty consecutive UP ticks after that = one failback decision. `touch /var/lib/tier0-controller/PAUSE` stops evaluation. **Automatic execution does not exist**; it is added only after the daily rehearsal has been green for a week. Until then the alert is the trigger and the same commands are run by an agent.

## Failover and failback (the commands)
```
sudo tier0-run tier0-failover.sh --promote        # vault+keystore, slice, standby gateway (refuses while 0docker answers; --force is human-only)
sudo tier0-dns plan                               # what DNS would change (dry run, ~430 records)
sudo tier0-dns failover --to 203.0.113.1 --apply   # writes /var/lib/tier0-dns/revert-<ts>.json
# ... later, 0docker healthy for 30 min ...
sudo tier0-dns failback --apply                   # exact inverse (values, TTL, comments); exit 3 = a record was changed since, skipped and reported
sudo tier0-run tier0-slice-promote.sh --teardown ; sudo tier0-run tier0-gateway-promote.sh --teardown-rehearsal
```
Swapping `--from/--to` is NOT the inverse: 153 names legitimately point at the 0mcp address.

   **Host keys must not change under the runner.** Proxmox derives a guest's cloud-init instance id from its cloud-init settings: any change plus a reboot is a "new instance", and cloud-init then regenerates the SSH host keys (default `ssh_deletekeys: true`). Prevented since 2026-10-18: `/etc/cloud/cloud.cfg.d/99-keep-ssh-hostkeys.cfg` (`ssh_deletekeys: false`) on VM 110 (nginx), VM 130 (docker-build) and VM 200, and `ssh_deletekeys: false` in the user-data of every guest the proxmox_guests role renders. A guest rebuilt from scratch needs the pin repaired (cross-check the fingerprint through `qm guest exec` on its hypervisor, never trust-on-first-use).
4. **GitHub**: add `/etc/tier0-runner/deploy_key.pub` as a READ-ONLY deploy key on baditaflorin/fleet-state.
5. **Builder (CT108)**: copy `/etc/tier0-standby/standby.crt` to `/etc/tier0/tier0-standby-infer.crt` and set `TIER0_EXTRA_CERTS=/etc/tier0/tier0-standby-infer.crt` in `/etc/tier0/tier0.env`, then run the snapshot, escrow and slice-sync jobs once. Verify: decrypt each latest artifact on this VM with the sealed key (hash equals the manifest).
Revoke everything by deleting the lines tagged `t0runner@infer-tier0`, the `t0jump` user and the deploy key.

| 1. **replay of recorded reality** (`controller/replay_pull.py` on the monitoring VM, `controller/replay.py`, fixture + `tests/test_tier0_controller_replay.py`) | the rule on REAL data: the 2026-10-13 outage is decided once, 4 min after it began, handed back once ~30 min after recovery; the nightly builder-backup stop and a 2 h single-app outage decide nothing; a rule that fires on ANY failing probe would have failed over every night | done: ~7 days of data (the probes exist since 2026-10-10; Prometheus keeps 15 days), 1 failover decision, 0 false positives |
| 2. executor scenario tests (`tests/test_tier0_executor.py`: fake clock/stages/DNS, failure injection: a stage fails, DNS fails then recovers, primary returns mid-run or mid-DNS, restart mid-run, PAUSE, busy lock, gate closed, one run per episode, no automatic failback, 400 seeded random fault schedules checking invariants) | the part that ACTS: partial failure, resume, no double promote, DNS only after the required stages, bounded retries; mutation-tested: 11 deliberately dangerous breakages of the executor are all caught | done (431 tests) |
| 3. daily full-cycle simulation on the runner (`executor/tier0_sim.py`) | the whole automatic path with the real stage scripts, real runner ssh, real DNS API and real authoritative servers on throwaway objects; found a real bug on its first run (verification judged the first look at DNS instead of polling) | done: clean ~170 s daily, abort ~70 s weekly, metrics `tier0_sim_*`, history feeds the gate |

| 5. one planned game day | the same thing with a real partition | after 2-4 |

**Promotion gate for automatic FAILOVER** (all of; the executor checks the machine-checkable ones itself and refuses `live` while any is missing, `sudo tier0-executor plan` lists them): 7 consecutive green daily rehearsals; a replay of all available data (at least the last 14 days once they exist) with 0 failover decisions that do not overlap a real all-probes-down window; rung 3 green for 7 days; a green DNS drill within 30 days; no `Tier0ControllerBlind` longer than 15 min during the shadow period; the PAUSE file tested. Automatic FAILBACK stays manual until the vault handback (demote, compare, merge, re-seed from the promoted node) is scripted and drilled.
To re-validate after changing the rule: on the monitoring VM `python3 replay_pull.py /tmp/series.json`, then `python3 replay.py /tmp/series.json`.

## Executor: modes, switching it on, switching it off
- `shadow` (default): on a controller failover decision it records "would run precheck -> vault -> slice -> gateway -> dns -> verify" and executes nothing.
- `sim`: only the daily simulation uses it (throwaway objects).
- `live`: the real failover. `echo live | sudo tee /etc/tier0-executor/mode` is refused in effect by the executor itself until: 7 consecutive green daily rehearsals, 7 consecutive green full-cycle simulations, a green DNS drill within 35 days, 7 days of controller history with the controller never blind for more than 15 ticks, no PAUSE file. The replay of recorded reality (rung 1) is re-run by hand before switching; alert `Tier0ExecutorLiveMode` fires while it is on.
- Kill switch: `touch /var/lib/tier0-controller/PAUSE` (stops the controller AND halts the executor between steps). `sudo tier0-executor status` shows the run, `ack` returns it to idle after a manual failback or clean-up.
- What it never does: tear down anything automatically in live mode (a promoted vault may already hold writes), fail back (the vault handback is not scripted), act while any vantage point says UP or cannot be confirmed down.

## DomainScope standby (VM 8101 on 0infer), 2026-10-17
DomainScope's web tier runs on VM101 behind the 0docker gateway. Its standby is VM 8101 on the 0infer hypervisor, a restored copy that stays OFF and SILENT until the failover starts it. Who does what:

| Piece | Where | What it does |
|---|---|---|
| `tier0-domainscope-snapshot.sh` (fleet-state, hourly :41) | CT108 | reads `.env`, compose file, 39 token files and the graph-writer key from VM101 through a key restricted there to one `tar` command, refuses implausible bundles, encrypts to the operator + sealed standby key, replicates to 2 sites, exports `tier0_domainscope_snapshot_*` |
| `tier0-domainscope-promote.sh` (fleet-state) | runner (VM704) | `--check` / `--rehearse` / `--promote` / `--teardown`: fetches + decrypts the newest bundle, hands it to `standby-ctl` through ONE forced-command ssh key (stdin only), `--promote` is ok only if the standby edge then serves the site |
| `standby-ctl` + `standby-ctl-ssh` (`host/`) | 0infer hypervisor | start / check / rehearse / activate / start-cron / deactivate of VM 8101 through `qm` and the guest agent; the fence lives HERE |
| nft DNAT + tailnet grant + `gateway-extra.json` | host, tailnet policy, runner | the standby edge reaches the VM through the hypervisor on exactly ports 23480/23481 and builds the DomainScope vhost from the CURRENT production config |

**Resting state** (what every run ends in and `standby-ctl check` verifies): VM stopped, net0 `link_down=1`, `onboot 0`, `protection 1`; inside the disk `tailscaled` masked (a restored copy carries VM101's tailnet identity: it must never reach a network before this is checked), no container running, every restart policy `no`.

**Verbs** (`standby-ctl <verb> [--bundle]`, bundle on stdin; exit 0 ok / 3 precheck / 4 refusing / 5 failed / 6 rehearsal skipped):
- `activate`: fence (the 0docker host answers on neither 22 nor 443 from the hypervisor AND a control target answers; unknown never counts as down; `/etc/standby-ctl/DISABLE` is a host-side kill switch), host memory, start with the link DOWN, silent check, bundle (re-validated, overrides applied: primary-LAN endpoints cleared, the hypervisor's gateway added to TRUSTED_PROXIES), link up, network check, read-only DB probe with the production DSN (TLS, 559 tables, primary), image tags, production `api` + `frontend` (never `cron`), health from the hypervisor. Re-runnable: a step that finds its postcondition met does nothing; an unusable bundle does not stop it (it runs on its older config and says so).
- `rehearse` (daily 05:48 UTC from the runner): THE SAME PATH as an activation, so what is tested is what will run: boot with the link down, silent check, bundle, link up, network, read-only DB probe with the production DSN, image tags (pulled and written back, exactly as an activation does), then the production `api` + `frontend` on the real ports 23481/23480 against the STAGING database, a 20 s settle window (the runner probes the edge path through the DNAT while it is up), teardown, power off, link down, resting-state check. Always ends resting, whatever failed; skipped (exit 6) when the hypervisor has < 9 GB available or the VM is in use. **The database swap is the dangerous part and is checked twice:** the production compose file reads `POSTGRES_DSN` through `env_file: .env`, so a shell variable would be silently ignored (found by rendering the compose file with a sentinel on 2026-10-17); the rehearsal therefore swaps the DSN line in the `.env` itself (restored byte for byte in the teardown, which also proves the `.env` names the production database again), refuses to start unless compose's RENDERED config names the rehearsal database (`stage_2026_...`), and stops what started unless the running containers do too. An activation runs the same two checks against the production database (`prod_2026_...`); a bundle whose `.env` names another database is refused. The staging `ansiblepguser` login of the standby's address is allowed by one narrow pg_hba rule (staging database only, TLS).
- **A step that runs out of time** (guest exit 124, e.g. `docker ps` blocked because `docker.service` never finished starting: the 2026-10-31 rehearsal, 603 s) leaves `guest_diag` in the run record `/var/log/standby-ctl/<ts>-<verb>.json`: one bounded script run in the guest right after the first timeout (systemd jobs still queued, unit states, the docker/containerd journal of this boot, kernel warnings, blocked processes, memory, disk), never calling docker, taken before the teardown adds its own wait. If the agent is wedged too the field says `unavailable`. The guest's own journal keeps only the current boot (journald `SystemKeepFree=5G` on a disk with about 5 GB free), so this record is the only account of such a hang.
- `start-cron`: only on an ACTIVE standby after 30 minutes, with the fence holding again (the singleton writer must not run beside a primary that may come back).
- `deactivate`: the failback, manual, never automatic.

**Images.** The `ghcr.io/baditaflorin` images of this stack can be pulled from the standby without a login (the first rehearsals pulled the new tags in about 20 s), so the rehearsal and an activation pull the tags the bundle asks for; the rehearsal keeps the standby's disk current, and an activation pulls again. If a pull ever fails (GHCR unreachable, a package made private) the standby falls back to the NEWEST tags it has on disk, reports `degraded` (older image than production) and goes on: an older image on the current database beats no site. `Tier0DomainscopeImagesLagging` fires when a rehearsal reports that lag for 36 h.

## Boundaries: what this does NOT cover (by design or not built)
- **Site loss only.** The controller and executor act when the 0docker HOST stops answering (ports 22 and 443 on its public address, from two vantage points). If the host answers but a guest is dead (for example the edge VM104 while sshd still answers), nothing fails over: the stage scripts refuse while "the site answers" (two writable vaults = split brain), by design. That case is alert-only today (`public-edge-critical` probes) and the remedy is repairing the guest; a narrow guest self-healing (start a stopped onboot guest outside backup windows) is a candidate, not built.
- **Same provider.** Both vantage points and the standby edge are in the same provider network: a provider-wide outage is not a case this can fix.
- **Failback and the vault handback** are manual (see above). **Domainscope prod** (VM101): the standby VM 8101 is started by the optional `domainscope` stage (section above). Not covered: a standby image that lags production (see Images), the singleton cron writer (never started automatically), Plane and the other containers of VM101 (not part of the standby), and the database itself (the standby uses the production primary on 0database; a replica exists on 0infer for a future promotion).
- **The live path has never run for real**: rung 2-3 exercise the same code with the REHEARSE flavour of the stage scripts; only a planned game day (rung 5) proves `--promote` end to end.
