# WS-0545: The nightly agent-history redaction canary scan

## Status

In progress. See the pull request for what was applied and when.

## Goal

The agent-history store holds every prompt, reply and tool call of the coding agents, so a secret that slips past redaction stays there. The canary proves, every day, that it does not: fake secrets of every redaction rule are written into a test session, shipped by a real collector, stored, and looked for. The store's API never returns `raw`, so the look at `raw` is a nightly SQL scan on the guest. The role (`agent_history_runtime`) already ships that scan, off by default because it needs a SQL file only the owner delivers. This change turns it on for the guest and writes down how the pieces fit.

## Change

- `inventory/host_vars/agent-history.yml` (new): `agent_history_canary_scan_enabled: true`, `agent_history_canary_scan_host: canary-mac14`. The role asserts the host starts with `canary-`, so the scan can never count a real laptop's history.
- `docs/runbooks/configure-agent-history.md`: a section on the canary: the dedicated host and its write token, the two launchd jobs on the Mac, how the SQL file is generated (`dbscan -maxAge 36h`) and delivered, what the three outcomes mean, how to prove both directions, and how to purge the canary rows.

The SQL file holds fake secrets only, is generated by agent-eval's `scripts/dbscan` and delivered to `/var/lib/agent-history/canary-scan.sql` (root, 0600) by the owner: it is never committed. A fresh guest without that file fails the role's assert on purpose ("deliver it, or leave the scan disabled").

Nothing in this change contacts a host. Applying the role is a recorded live step done after the merge.
