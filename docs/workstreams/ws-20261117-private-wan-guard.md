# Private WAN egress incident, 2026-11-17

Status: emergency containment in progress. Base: origin/main a520e25e644a6a84b29bb49464ada2fded0e5c15.

Hetzner reported private-address UDP packets leaving the public interface of a fleet hypervisor. The earlier October fix in PR 645 protected forwarding on another hypervisor, not this host; it also did not cover host-originated traffic. On 2026-11-17, a separate `inet private_wan_guard` nftables table was installed manually on the affected host. Its output and forward base chains drop RFC1918, CGNAT, and link-local IPv4 destinations only when leaving the public interface. No existing firewall table was flushed. The packet counters increased on both chains. This is containment, not proof that private service routes are correct.

The affected hypervisor's public interface and management routes must be confirmed before applying this pattern elsewhere. The live table is ephemeral until a separately managed boot-time loader is in place. Do not flush the ruleset. The original notice requires a provider test and statement; neither has yet been completed. Further investigation must attribute endpoint discovery, audit routing and peer advertisements, verify no WAN leakage and normal public/private flows, and add persistent fleet-wide controls with behavioral regression tests.

## Live containment and evidence

At 16:18–16:19 UTC the affected hypervisor received an atomic standalone nft table and an enabled `private-wan-guard.service`, ordered before `network-pre.target`, loading `/etc/private-wan-guard/rules.nft`. The example in `config/private-wan-guard/` records the live rule structure and loader. The actual uplink is deployment-specific. No existing tables were flushed. A syntax check and `systemd-analyze verify` completed; `systemctl` reported the service enabled and active. A host UDP send to an unrouted private address was denied with EPERM and incremented the output drop counter. Forward counters increased from real traffic. A 20-second raw outgoing capture on the public interface observed zero packets with private, CGNAT, or link-local IPv4 destinations; the public CI endpoint returned HTTP 200. This is a bounded observation, not proof of immunity to every future configuration change. The service has not been reboot-tested. Whole-ruleset flushes could remove its active table while systemd still reports active.

The Oct 30 notice concerned a different host; PR 645 protected only forwarded traffic on that host's WAN bridge. The Nov 17 notice concerns this hypervisor. At least the gateway VM and builder container generate UDP 41641 discovery attempts toward many peer interface addresses; one peer exposes Docker bridge addresses. Tailscale on the builder runs in userspace. Unrouted candidate addresses fall through to the public default route and guest NAT; the affected host itself also originates private WAN-bound traffic. This is supported by live route lookups, packet capture and guard counters. It is not yet established which change triggered the peer discovery burst, nor whether missing routes explain reported internal service failures. The monitoring guest's current peer and interface state does not establish who advertised every historical candidate.

Follow-ups: audit all public hypervisors and both output/forward hooks, make policy continuously monitored and resilient to ruleset replacement, exercise behavior in isolated network namespaces and at boot, investigate peer endpoint advertisement and actual required private subnet routes, check internal-service flows, run Hetzner's test, and prepare an accurate statement. Avoid claiming universal prevention until fleet coverage and reboot/flush behavior are proved. Plane issue sync failed because the configured token was rejected; Git workstream is the fallback.

The test reads the canonical collection template, rather than the ignored duplicate under `roles/`, and checks both chains and ordering. The focused test suite passed (10 tests). ## Further fleet containment

At approximately 16:29–16:30 UTC, equivalent standalone output and forward guards were installed on the other three checked public hypervisors. Their verified public interfaces were determined on each host, and each loader was enabled with `After=nftables.service` and `Before=network-pre.target`. Controlled sends to an unrouted private destination failed with EPERM on all three; both output and forward counters recorded traffic, and an HTTPS request to the public CI service returned 200 from each host. The first host's loader is ordered after `local-fs.target` and before `network-pre.target`, with its nftables service disabled. Boot behavior has not been tested. On hosts whose existing nftables configuration flushes the whole ruleset, a subsequent reload can erase the guard while its oneshot service still appears active: this is a critical open gap requiring monitored and managed integration, not a fleet-wide prevention guarantee.

The builder's live Tailscale network map showed 246 endpoint candidates for the local Docker host and 100 for an inference runtime. The Docker host currently has 244 IPv4 interface entries, many Docker bridges matching the candidate addresses. These observations explain the candidate-list breadth; they do not establish what triggered the November burst or attribute it to an operator. On the Docker host, apt history records upgrades from 1.102.2 to 1.104.4 on November 2 and to 1.104.7 on November 13; the impact of those upgrades on endpoint discovery has not been isolated.

Hetzner's portal requires a human-written statement and an explicit human-authorship attestation. The ticket remains open; no statement or recheck was submitted. The deadline is 2026-11-18 07:48 UTC.

## Independent physical-egress guard and health

The five public hypervisors now run the independent physical-uplink traffic-control guard, alongside the existing interface-scoped nft guard. An enabled device-bound systemd unit restores the TC filters when its NIC appears; a one-minute timer verifies and reconciles both layers and exports node-exporter metrics. Each host's TC unit was restarted and verified, both health metrics read 1, and public HTTPS remained functional. No hypervisor was rebooted. A disposable two-network-namespace rig proved that private traffic reaches the peer before the guard, is then dropped, that public traffic passes, that a full nftables flush does not remove TC protection, and that removal restores the baseline. A second isolated rig removed both nft and TC protection and proved the health script restores them and reports healthy. Capability tests also passed in disposable namespaces on all five production kernels. Neither simulated tests nor a one-minute reconciliation can guarantee against every privileged change, hardware failure or configuration error.

Monitoring's Gitea liveness probe was independently diagnosed: the health endpoint returns 200 from the hypervisor, while the monitoring VM times out. A fresh network-policy snapshot reports that the monitoring-to-Gitea TCP flow is denied at both the Proxmox and guest input layers. The proposed policy and host inventory add only this source and port. There is no evidence tying this particular missing allowance to the private-address packets reported by Hetzner. The report's attachment contained IP addresses and ports, not a list of domains.

The original baseline CI schema error was corrected by making an already-merged, live-apply-pending agent-history workstream's source ownership read-only; the private WAN workstream also declares its own ownership. The previously claimed root-cause link to an unnamed agent or a specific Tailscale version remains unproven.

Prometheus now scrapes both healthy guard metrics on all five hosts, and the deployed guard alert group reports all three rules healthy. The Gitea policy apply is planned as exactly three additions (Proxmox input, live guest input and persisted guest input); the service endpoint was healthy from the host before the change. The repository release manager refused a formal release because the existing registry contains 105 in-progress workstreams and expired waiver blockers; no formal release or tag has been cut. The repository version bump in this integration records the requested merge separately from a formal release.

## Edge identity discovery failure

At 17:09 UTC a separate production issue was confirmed and temporarily repaired. The edge authentication proxies repeatedly failed OIDC discovery because the identity hostname resolved to the hypervisor's public address, whose hairpin connection was refused. The same HTTPS discovery request, with certificate verification, returned 200 against the local private edge address. A locked manual addition to the edge VM's `/etc/hosts` mapped only the identity hostname to that private edge; the previous file was preserved beside it with a dated backup. Both affected oauth2-proxy units recovered automatically, and seven frontends returned 302 sign-in redirects. Browser sign-in has not yet been verified. Existing role code already attempts this mapping; investigate why it did not persist and make it idempotent and monitored before considering this durable. This failure is distinct from the private IP egress caught by Hetzner.

Cloud-init logs show that `config-update_etc_hosts`, which runs every boot, rewrote the edge VM hosts file at its last boot and removed the identity mapping. The live cloud-init Debian hosts template was updated under the same lock, with a dated backup; the cloud-init renderer produced exactly one expected mapping in a read-only test. The canonical edge OIDC role now writes both the active hosts file and, when present, the cloud-init template, and fixes the hosts-matching regular expression so repeated runs match rather than append duplicate entries. An unauthenticated browser reached the Authentik login page from a protected frontend; authenticated login has not been tested.

## Internal public-name hairpin

The monitoring VM also could not reach the identity and task frontends using their public DNS names, although the same TLS requests reached the private edge successfully. The hypervisor only DNATed web traffic arriving from its public bridge; connections from the private bridge to the hypervisor's public address reached no listener. At approximately 17:30 UTC a narrowly scoped separate NAT table was added manually: private-subnet traffic to the hypervisor's public IPv4 TCP 80/443 is DNATed to the private edge, and same-subnet replies are SNATed to the private gateway. No unrelated firewall table was flushed. Source addresses at the edge for these hairpin flows are the gateway, a deliberate logging and client-IP tradeoff; direct private calls retain their original source. Before the live change an isolated bridge/veth test proved the original failure, successful public-address hairpin, direct-private access and rollback. After the change, the monitoring VM's default DNS paths to the identity and task hosts returned HTTP 302, Gitea returned 200, and the NAT counters incremented. The live standalone table currently disappears after a full ruleset flush or reboot and needs committed persistent deployment before the incident is complete.

The immediate hairpin table is now included from the hypervisor's `/etc/nftables.conf` through a separate owned file. The existing config was backed up, the complete resulting ruleset passed `nft -c`, and the original was compared before atomic replacement; the firewall was not reloaded. The canonical `proxmox_network` template now contains equivalent scoped rules, so a later managed converge need not retain the temporary include. A namespace rig renders the actual template and verifies baseline failure, repaired public-name path, direct-private access and rollback. A 12-second capture on the physical uplink during live identity/task requests saw zero outbound frames addressed to the host's public HTTP(S) endpoint. Reboot and a full production ruleset reload were not attempted.
