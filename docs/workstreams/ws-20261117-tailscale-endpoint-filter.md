# Tailscale endpoint discovery and Plane automation

Status: investigation. Base: `f7e358e24ca022369445c45e92516ea062ce130b`.

The private WAN guards from PRs 698 and 699 remain active and monitored. The incident traffic is still being attempted and dropped, so filtering alone does not resolve discovery.

A live builder network map contains hundreds of private endpoints across multiple container-host peers. The current Tailscale release scans active interface addresses, including container bridges. An upstream proposal for configurable endpoint interface exclusion remains unmerged. A replacement must preserve usable LAN and public endpoints, survive service updates and restarts, avoid exposing credentials, and be proved with a bounded canary and rollback before broad deployment.

Plane is currently running. Its private API returns HTTP 200, both configured API keys authenticate through an SSH loopback tunnel, and the AW project contains six historical work items. The previous invalid-token diagnosis was incorrect: no local tunnel was listening. The connection failure was collapsed into a token-invalid error. Repair the access path and error classification, and verify an actual workstream sync.

A user-editable provider response draft was prepared in ignored local incident state; it has not been sent or submitted.

## Prepared source-level canary

The upstream proposal is pinned in `config/tailscale-endpoint-filter/`. A static daemon was built on an approved remote builder against the exact installed upstream release; network-monitor tests passed, including preservation of an ordinary LAN address while excluding Docker bridges. A disposable container exercised the timed-canary installer, explicit rollback, conflict refusal, confirmation, and fallback/alert behavior when the vendor version changes. None of this proves fleet-wide endpoint reduction until a live canary is independently measured. On package-version drift the wrapper uses the vendor daemon and the existing WAN guard remains required; monitoring must alert so the patch can be rebuilt and reviewed.

At 19:48 UTC on 2026-11-17, one Docker runtime host received the committed canary with a five-minute rollback timer. An independent peer's view changed from 241 advertised Docker bridge addresses to zero, while retaining the host's usable LAN endpoint. Tailscale ping, the host proxy health endpoint, the existing WAN guard, the filter metric, and fresh TLS-verified Gitea and Grafana browser sign-in all passed before the canary was confirmed. A second peer independently observed zero bridge addresses. The alert group was loaded and verified on the monitoring VM, and Prometheus scraped a healthy canary metric. Other peers still advertise container addresses. The builder subsequently experienced a transient period of high I/O wait; its Tailscale API recovered, but the cause of the host's I/O pressure is unproven. The affected hypervisor's previously reported NVMe SMART failure remains a separate risk.

Before extending the canary, inventory showed that some node exporters use a nested textfile directory. The health script now detects and validates the exporter directory from its running process; the isolated installer test verifies both the default and nested layouts. This correction has not yet been rolled out to the initial canary.

Gitea and Grafana were independently verified using fresh Firefox profiles, TLS validation, and the dedicated non-admin test identity. Gitea completed Authentik sign-in with a non-admin account; Grafana completed Authentik sign-in with Viewer role. The Plane workstream issue was created and read back through a locally scoped SSH tunnel; the sync now establishes and closes the configured tunnel automatically and distinguishes a refused connection from an invalid API key.

At approximately 20:06 UTC, a second, lightly loaded runtime running Tailscale 1.104.5 was filtered. Its peer map no longer advertised its Docker bridge address, retained the LAN address, and its pre-existing relayed Tailscale connection and node-exporter metric worked. The hypervisor nftables and traffic-control guards passed. The first attempt safely rolled back because a direct-only ping check rejected a functioning relay; the confirmed retry used a relay-aware ping and an actual metric fetch. The other hosts remain outstanding.

The monitoring VM was missing the second runtime's target even though it was already present in committed inventory. Its validated Prometheus configuration now includes that target; both runtime filter metrics are healthy in central Prometheus. The alert group also detects a previously observed metric disappearing for up to 24 hours. At that stage, never-scraped and longer-missing hosts still needed separate coverage; the expected-runtime job described below was added afterwards.

At 20:12 UTC, a third runtime with active container services was filtered. An independent peer saw its 98 bridge endpoints fall to zero and retained the LAN endpoint. Tailscale, the monitoring metric, a running service health endpoint, Docker health, and both WAN guard layers passed before confirmation. A first attempt rolled back on a short discovery timeout; the successful retry allowed a bounded settling interval. Central Prometheus now scrapes the target using the newly declared inventory entry. Other peers still require individual rollout and verification.

At 20:18 UTC, a fourth runtime was filtered through its hypervisor guest agent, using a short-lived transfer bound to the private guest network. A peer observed its 20 bridge endpoints fall to zero with the LAN endpoint retained. Tailscale, a running service health endpoint, Docker health, both WAN guard layers, and the filter metric all passed; central Prometheus scraped the metric. The hypervisor showed substantial I/O pressure during the operation; further work on it was paused and the cause has not been established.

The managed monitoring inventory initially registered the first four protected runtimes in a dedicated textfile-only scrape job. Rules alert when a registered target is unreachable or its filter metric is absent, even if it has never been scraped; they also alert if the whole expected-target job disappears. All four dedicated targets returned healthy metrics. Each future rollout must register its target, and independent inventory auditing is still required to detect removal of a single target.

An additional runtime hosting the work board and CI service was restored to the stock daemon after two rollback-protected attempts. The first failed because its node exporter is reachable from monitoring on the LAN, not the tested tailnet address. The second failed because a discovery ping timed out; the same monitoring peer briefly timed out after rollback, while LAN monitoring and the work board API remained reachable and a different peer successfully connected via relay. The peer-specific path was investigated before the successful retry described below.

At 20:32 UTC, the runtime hosting the work board and CI was confirmed after a third, bidirectional check. An independent peer saw its 24 bridge endpoints fall to zero and retained the LAN endpoint. The work board API, LAN metrics path, Tailscale in both directions, and both WAN guard layers passed; the dedicated expected-host job now scrapes all five protected runtimes as healthy. The previously observed discovery delay also occurred on the stock daemon and cleared when the other peer initiated a connection.

At 20:36 UTC, the monitoring VM was confirmed after a rollback on the first attempt: the first check used an exporter path blocked by its existing firewall, while the successful retry used Prometheus's established local scrape path. An independent peer observed its two bridge endpoints disappear while retaining the LAN address. Bidirectional Tailscale, Prometheus readiness, the filter metric, and both WAN guard layers passed. All six protected runtimes are now registered and healthy in the expected-host scrape job.

At 20:41 UTC, the public hypervisor serving as a subnet router was confirmed. An independent peer observed its four Docker bridge addresses disappear while retaining the internal LAN bridge. Bidirectional Tailscale, the filter metric, both WAN guard layers and two real internal exporter routes passed. The first attempt interrupted its own Tailscale SSH session and was restored over host-key-verified direct SSH; the successful retry used that independent path. All seven protected nodes are registered in the expected-host monitoring job. The host's RAID mirrors were intact and IO pressure was low, but one NVMe device reports failed SMART health and requires separate attention.

The incident log also contains private LAN addresses, so suppressing container advertisements alone does not stop all off-link private discovery attempts. A downstream sender filter was prototyped to allow private IPv4 discovery only on directly connected subnets of eligible interfaces and to leave public and relay destinations available. Focused sender and network-monitor tests passed on both supported releases; independent rebuilds produced identical artifacts. The upgrade harness tests rollback after a simulated restart failure. A rollback-protected sender rollout is now active on six of the seven registered nodes. The remaining registered runtime is on a hypervisor with severe I/O pressure, and other unregistered peers also remain to be assessed; the WAN guards remain essential for those nodes.

Sender-specific monitoring is prepared so a registered node running the older advertisement-only filter cannot appear fully protected: the new health metric and missing-sender alert distinguish the two. The sender-specific missing-guard alert was validated with promtool and loaded into Prometheus during the staged sender rollout.

At 21:48–21:54 UTC on 2026-11-17, a live rollback drill restored the previous filtered daemon, and a subsequent sender canary suppressed 12 off-link candidates while a capture across its restart observed zero off-link private UDP packets. Five more nodes were upgraded individually, with independent peer endpoint checks, service and routing checks, the guard metric, and the WAN guards verified before confirmation. Central Prometheus reported the sender metric healthy on all six and no failed probes or down targets. One registered runtime remains on the prior filter because its hypervisor showed severe I/O pressure. Other peers have not yet been upgraded or enrolled; a vendor package version change also falls back to the stock daemon. The WAN guard must remain enabled, and no fleet-wide or reboot-proof claim is made.
