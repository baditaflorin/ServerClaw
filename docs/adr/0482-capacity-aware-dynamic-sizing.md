# ADR 0482: Capacity-Aware Dynamic VM Sizing

**Status**: ACCEPTED
**Date**: 2026-05-11
**Decision**: A deployment's per-VM resource allocations (RAM, CPU, disk) are *computed* at bootstrap time from probed host capacity and a service-class sizing policy. They are NOT copied from another deployment's committed inventory.

---

## Context

### Problem

Today, every deployment's `proxmox_guests` list (in `inventory/host_vars/proxmox-host.yml` or `.local/deployments/<slug>/topology.yml`) carries **hard-coded** `memory_mb`, `cores`, and `disk_gb` for each VM. Those numbers were sized for lv3's original Hetzner box and have been propagated unchanged when the platform is forked.

The 2026-05-11 0fork incident demonstrates the failure mode:

- 0fork runs on an AX41-NVMe with **64 GB physical RAM**.
- The inherited topology allocates **~180 GB of guest RAM** (17 VMs sized for lv3's larger original host).
- The Proxmox kernel falls back to swap (~28 GB used in normal operation).
- Adding any new VM, or restarting one cleanly, pushes the host into severe memory pressure: SSH banner exchange times out, Docker logging hiccups cause Harbor's `nginx` + `harbor-portal` to silently exit-128 and stay exited for 5 days.
- The "fix" — shutting `runtime-ai` and right-sizing `docker-runtime` from 24 GB to 16 GB — was a manual one-off.

The same operator who forks the platform tomorrow onto a different-sized Hetzner box (or any other cloud host) will hit the same wall. The platform is currently *not portable* in a real-data sense even though ADRs 0407 / 0424 / 0440 / 0481 made it textually generic.

### Why this matters strategically

The platform's promise (ADR 0407 onward) is **forkability**: any operator stands up the same stack on their own infrastructure with one command. That promise breaks if the operator must hand-edit RAM allocations to fit their host. A real fork experience is:

```
make new-deployment slug=mycorp apex=mycorp.example
# operator fills in identity.yml + connection.yml
make bootstrap        # everything else — sizing included — is derived
```

For that to work, **sizing must be a function of the target host, not the source deployment**.

### Why not just "manually tune at install"

We could keep the hard-coded numbers and tell operators to edit them. We tried that. It produces:

- The lv3-derived numbers persist into clones because nobody knows which numbers are load-bearing.
- Operators err on the side of "leave it alone, looks right" — and end up swapping.
- When an operator does shrink, they shrink the wrong VM (e.g. postgres) because they don't know the platform's internal resource-pressure model.
- Changes to the committed inventory's sizes affect every deployment, which is the wrong scope.

The right scope is **per-deployment, derived once, written into that deployment's `topology.yml`**.

## Decision

### 1. Three new inputs to topology generation

| File | Source | Purpose |
|---|---|---|
| `.local/deployments/<slug>/capacity.yml` | Generated by `make probe-capacity slug=<s>` | What the host actually has: RAM, cores, disk free, network |
| `config/sizing-policy.yml` (committed) | Operator-curated, repo-wide | Per-service-class allocation rules + priorities |
| `.local/deployments/<slug>/profile.yml` | Operator-authored | Which service profiles are enabled (ADR 0441) |

These three feed a **resolver** that produces a per-VM allocation matching the host's actual capacity. The resolver writes the result into `.local/deployments/<slug>/topology.yml`, replacing the hand-curated `proxmox_guests` list.

### 2. The capacity probe (`scripts/capacity_probe.py`)

Run-modes:

- **Local probe (preferred)**: SSH to the Proxmox host using the deployment's `connection.yml`, read `/proc/meminfo`, `nproc`, `pvesm status`, `ip -j addr`, and `df`. Emit a structured `capacity.yml`.
- **Operator-declared (fallback)**: When the host isn't reachable yet (cold provisioning), the operator can write `capacity.yml` by hand. The probe validates it against `config/contracts/deployment-v1/capacity.schema.json`.

Schema (excerpt):

```yaml
schema_version: 1
probed_at: 2026-05-11T20:30:00Z
probed_via: ssh   # or "operator"
host:
  ram_total_mb: 64512
  ram_reserved_mb: 4096   # host overhead — Proxmox + ZFS ARC
  cores: 16
  threads: 32
  storage:
    - name: local
      type: zfs
      total_gb: 1024
      free_gb: 880
  networks:
    public_ipv4: 203.0.113.3
    private_bridges: [vmbr1, vmbr10]
```

Probe is **read-only** and idempotent. It is *not* a converge step — it's a planning input.

### 3. The sizing policy (`config/sizing-policy.yml`, committed)

Per-service-class allocation, with priority tiers so the resolver knows what to shrink first under pressure.

```yaml
schema_version: 1
classes:
  nginx:
    priority: critical          # never below min
    cpu: { min: 1, preferred: 2, max: 4 }
    ram_mb: { min: 1024, preferred: 4096, max: 8192 }
    disk_gb: { min: 16, preferred: 32, max: 64 }
  postgres:
    priority: critical
    cpu: { min: 2, preferred: 4, max: 8 }
    ram_mb: { min: 2048, preferred: 8192, max: 32768 }
    disk_gb: { min: 32, preferred: 96, max: 512 }
  docker-runtime:
    priority: critical          # hosts the 7 platform services
    cpu: { min: 2, preferred: 4, max: 12 }
    ram_mb: { min: 4096, preferred: 16384, max: 32768 }
    disk_gb: { min: 64, preferred: 128, max: 512 }
  runtime-control:
    priority: critical          # Keycloak, Harbor, OpenBao
    cpu: { min: 2, preferred: 4, max: 8 }
    ram_mb: { min: 4096, preferred: 12288, max: 24576 }
    disk_gb: { min: 64, preferred: 128, max: 256 }
  monitoring:
    priority: important
    cpu: { min: 2, preferred: 2, max: 4 }
    ram_mb: { min: 2048, preferred: 8192, max: 16384 }
    disk_gb: { min: 32, preferred: 64, max: 256 }
  postgres-replica:
    priority: nice-to-have
    cpu: { min: 1, preferred: 2, max: 4 }
    ram_mb: { min: 1024, preferred: 4096, max: 8192 }
    disk_gb: { min: 32, preferred: 96, max: 256 }
  runtime-ai:
    priority: optional          # forks usually omit
    requires_capability: gpu
    cpu: { min: 4, preferred: 6, max: 12 }
    ram_mb: { min: 8192, preferred: 16384, max: 65536 }
    disk_gb: { min: 64, preferred: 128, max: 512 }
  # … one entry per service class …

profile_defaults:
  core:    [nginx, runtime-control, docker-runtime, postgres, monitoring]
  full:    [nginx, runtime-control, docker-runtime, runtime-general, runtime-comms, runtime-apps,
            postgres, postgres-replica, postgres-apps, postgres-data,
            monitoring, backup, coolify, coolify-apps, artifact-cache, docker-build, runtime-ai]

priority_order: [critical, important, nice-to-have, optional]
```

The policy is committed because it encodes platform knowledge (what depends on what, what is safe to shrink) that applies to every deployment. Operator overrides land in `.local/deployments/<slug>/profile.yml` (already exists, ADR 0441) via `extra_services` / `disabled_services` / `service_overrides`.

### 4. The resolver (`scripts/resolve_topology.py`)

Algorithm:

1. Load `capacity.yml`, `sizing-policy.yml`, `profile.yml`.
2. Expand the enabled service set from profiles (already implemented in `scripts/deployment.py:resolve_enabled_services`).
3. For each enabled service's class:
   - Start at `preferred` for ram/cpu/disk.
4. Sum across all enabled classes. If `sum_ram > capacity.ram_total_mb - capacity.ram_reserved_mb`:
   - Walk `priority_order` in reverse (`optional → critical`).
   - For each class at that priority, shrink `ram_mb` toward `min` proportionally to its over-allocation share.
   - Stop when sum fits.
   - If even with everything at `min` the host doesn't fit, **fail loudly** — the platform genuinely doesn't fit on this host; emit a report listing which classes would need to be disabled.
5. Same algorithm for CPU and disk independently.
6. Emit `topology.yml` with the computed `proxmox_guests` list, each carrying:
   - `memory_mb`, `cores`, `disk_gb`
   - **`balloon: <40% of memory_mb>`** — always enable ballooning (lesson from the 0fork incident)
   - Standard fields (ipv4, gateway4, vmid, role, etc.) carried over from the static template.
7. Stamp the file with `generated_at`, `capacity_hash`, `policy_hash`, `profile_hash` for traceability.

### 5. Always-on ballooning (load-bearing default)

Every VM the resolver emits gets `balloon: <40%-of-ram_mb>`. The 0fork incident showed that with `balloon: 0`, the host cannot reclaim idle RAM from over-provisioned VMs — it falls back to swap, then SSH degrades, then operators cannot remediate. Ballooning is no longer an optional knob; it is part of the default policy.

(Operators can override via `service_overrides` in `profile.yml` if a specific workload truly cannot tolerate ballooning — e.g. databases pinning shared_buffers. That escape hatch stays.)

### 6. The `make` surface

| Target | Purpose |
|---|---|
| `make probe-capacity` | Connect to the deployment's Proxmox host, write `capacity.yml`. |
| `make resolve-topology` | Run the resolver, write `topology.yml`. Idempotent. Diffs against existing topology and shows what changed. |
| `make new-deployment slug=X apex=Y` | After scaffolding identity/profile/connection, call `probe-capacity` + `resolve-topology` automatically so the deployment is bootstrap-ready in one command. |
| `make plan-capacity` | Show what would be generated given the current inputs, without writing. Useful for "would my service fit on this host?" pre-purchase planning. |

### 7. Out of scope (for this ADR)

- **Live resize of running VMs.** The resolver writes `topology.yml`; applying it to an already-bootstrapped deployment requires either a VM reboot (for memory/disk changes) or a per-service decision. A follow-up ADR will define a `make apply-topology` that diffs current vs desired and proposes a migration plan.
- **GPU/AI host detection.** `requires_capability: gpu` is in the schema; the probe will need a follow-up enhancement to detect NVIDIA GPUs. Until then, AI classes are skipped unless the operator opts in via profile.
- **Multi-host clusters.** This ADR assumes one Proxmox host per deployment. ADR 0424's collapsed-topology pattern is the current shape for forks. Cluster awareness is future work.

## Consequences

### Positive

- **Real portability.** `make new-deployment` becomes the actual one-command fork experience the platform was already pretending to offer.
- **No more lv3-sized topologies on smaller hosts.** The 0fork incident's root cause becomes structurally impossible.
- **Sizing is auditable and traceable.** Every `topology.yml` carries the hashes of the inputs that produced it. "Why does this VM have 16 GB?" is answered by `(capacity, policy, profile)`, all of which are versioned.
- **Operator power inverts correctly.** Operators describe *which* services they want (profile). The platform decides *how big* each gets (policy + capacity). Today operators get a hard-coded answer to both; that's wrong.

### Negative

- New surface area to maintain: capacity schema, policy schema, resolver, three new make targets, two new ADRs of follow-on work.
- Resolver bugs are high-blast-radius (could over- or under-allocate critical services). Mitigated by:
  - Schema validation at every step.
  - `make plan-capacity` for dry-run preview.
  - Per-class `min` floors that protect against under-allocation.
  - The resolver is purely deterministic — same inputs always produce same outputs (hashes verify this).
- Existing committed `proxmox_guests` lists become redundant once every deployment runs through the resolver. They stay as reference / fallback for the "operator declares capacity by hand" path.

### Migration

For existing deployments (lv3, 0fork):

1. `make probe-capacity slug=0fork` — writes `capacity.yml` from the live host.
2. `make resolve-topology slug=0fork` — generates new `topology.yml` reflecting actual capacity.
3. Diff: shows that on 0fork's 64 GB host, the resolver would never have over-allocated to 180 GB; would have produced a coherent ~50 GB topology with ballooning enabled by default.
4. Operator decides whether to apply (which requires VM reboots / resizes).

For new deployments: `make new-deployment` runs the full chain end-to-end.

| Phase | Deliverable | Effort |
|---|---|---|
| 0 | This ADR + ws-0483 + capacity/policy schemas under `config/contracts/deployment-v1/` | Done in this PR |
| 1 | `scripts/capacity_probe.py` — read-only probe; `make probe-capacity` target | 1 day |

| 3 | `scripts/resolve_topology.py` — the resolver; `make resolve-topology` + `make plan-capacity` | 2 days |
| 4 | Wire into `make new-deployment` so the full chain runs end-to-end | 0.5 day |
| 5 | Backfill: re-probe + re-resolve lv3 and 0fork, diff against current `topology.yml`, document what would change | 0.5 day |
| 6 | `make apply-topology` — separate ADR; defines safe live-resize/migration semantics | follow-up |

Phase 0 lands with this commit. Phases 1–5 are tracked in ws-0483 and can be picked up in any order, though 1→2→3→4 is the natural sequence.
