## Context

Phases 1 and 2 closed the highest-leverage drift gaps. The remaining
Phase 3 items (7, 8, 9, 16, 17, 18, 19 from the 20-change review) target
two themes:

| Theme | Items | Owner |
|---|---|---|
| Structural deduplication | 7, 8, 9 | ws-0438 phase 2 (in flight) |
| LLM ergonomics + traceability | 16, 17, 18, 19 | this ADR |

Phase 3 is harder than Phase 1/2 because none of the four LLM-ergonomics
items have a runtime drift signal — they pay off only when the next
agent (human or LLM) opens a worktree and tries to act on the
codebase. The risk profile is high-leverage-per-line-of-code but
zero-feedback-until-the-next-task.

## Decision

Three deliverables, ordered light-to-heavy:

### Item 17 — Status-context tag in the ADR index

`docs/adr/.index.yaml` already exposes `implementation_status` per ADR
(`Proposed`, `Implemented`, `Accepted`, `Partial`, `Not Implemented`,
`Deprecated`). What's missing for the LLM is the *meta* — a one-word
hint on whether the ADR describes the **current state**, the
**goal state**, or **historical state**.

This matters because an LLM reading a Proposed ADR can mistake it for
the current contract (the failure mode my own ADR 0445 review
explicitly called out). Adding a `currently_describes` field driven
from `implementation_status` makes the mental model explicit:

| `implementation_status` | `currently_describes` |
|---|---|
| `Implemented` | `current_state` |
| `Accepted` | `current_state` |
| `Partial` | `mixed_state` |
| `Proposed` | `goal_state` |
| `Not Implemented` | `goal_state` |
| `Deprecated` | `historical` |

Surface in `to_entry` and `to_compact_entry` so every shard carries it.
Tests pin the mapping so a future status-vocabulary expansion is forced
to update both sides.

### Item 19 — Workstream → ADR → role traceability matrix

A single generated `build/traceability.yaml` joining three sources of
truth that today live in three trees:

- `workstreams/active/*.yaml` — workstream → ADRs implemented (`adr:`,
  `depends_on:` fields)
- `docs/adr/.index.yaml` — ADR → keywords + status
- `workstreams/active/*.yaml::shared_surfaces` — workstream → role/file
  paths touched

The output answers "what's the state of multi-deployment work?" by
reading one file. Today an LLM must crawl all three trees and
reconstruct the join.

Generated by `scripts/generate_traceability.py --write`. Validated in
`validate_repo.sh` as `validate_traceability` (advisory) — flags
workstreams whose `adr:` doesn't resolve to a real ADR, or whose
`shared_surfaces` paths don't exist on disk.

### Item 16 — Per-service onboarding cards (deferred — design first)

Originally proposed as `build/onboarding/services/<name>.yaml` per
service. Survey shows `build/onboarding/service-catalog.yaml` already
covers a flattened view; the per-service card design needs more
thought before generating files that may duplicate existing content.

Tracked as phase 3 of this workstream; ADR 0447 phase 4 picks it up
once items 17 + 19 land and we can measure their incremental value.

### Items 18 (single overrides source) + 7 (auto-generate role pairs)

Both heavy structural refactors. Tracked as deferred dependencies of
ws-0438 phase 2 sweep; this ADR does not own them.

## Acceptance Criteria

- Every entry in `docs/adr/.index.yaml` carries a `currently_describes`
  field whose value is one of the five literals above.
- `scripts/generate_traceability.py --write` emits
  `build/traceability.yaml` with at minimum: every active workstream
  → its ADR(s) → its shared surfaces; ADR keywords; ADR
  implementation_status.
- The traceability validator in `scripts/validate_repo.sh` flags broken
  workstream→ADR refs and missing shared-surface paths.
